Documentary draft · 0.5 not published

Prepare a 0.4-to-0.5 migration

The proposed 0.5 line keeps the two public V1 formats stable while retaining exact engine identity. That means the files look familiar, but every runtime artifact still has to be regenerated.

This is planning documentation, not an upgrade instruction. Package 0.5.0 and an associated release candidate are not published. Keep production and test fixtures pinned to apizit-linking==0.4.0 until the release channel says otherwise.

What is planned to remain unchanged

  • User-authored Linking manifests continue to declare version: 1.
  • The closed runtime-artifact envelope continues to declare version: 1.
  • The artifact remains a generated, opaque build output rather than a file users or adapters edit.
  • create_app_from_runtime_artifact remains the supported FastAPI adapter entry point.
  • The legacy create_app_from_runtime_routes bridge is planned to remain for this following minor under the 0.x deprecation policy.

Why recompilation is mandatory

The artifact envelope carries an exact engine_version. A proposed 0.5 runtime must reject an artifact compiled by 0.4.0 even though both artifacts declare runtime artifact version: 1. Format version 1 says the envelope has the same contract; exact engine identity says which implementation verified and serialized the callable metadata.

Re-run the compiler with the exact released engine. Never replace engine_version in JSON, copy routes between artifacts, or suppress the mismatch check.

Response scope is documentary only

Response wording and limits can be clarified in the 0.5 documentation, but this public preparation does not introduce declarative status codes, custom response headers, new response models, or streaming behavior. Such behavior needs a separately reviewed and tested contract. Until that exists, the documented V1 response boundaries remain authoritative.

Project-owner checklist after publication

  1. Read the final 0.5 release notes and confirm the draft label is gone.
  2. Install the exact version from PyPI in a clean test environment.
  3. Run apizit-linking validate against the unchanged manifest v1.
  4. Compile a new artifact with the 0.5 engine; keep artifact version 1.
  5. Run startup, success, conversion-error, and business-error tests.
  6. Replace only generated deployment outputs after the tests pass.

APIZIT must re-pin and rebuild

APIZIT currently consumes Linking as a separate released framework. Once, and only once, the 0.5 package exists on PyPI and the integration suite passes, APIZIT must:

  1. change its exact build and runtime pin from 0.4.0 to the released 0.5 version;
  2. compile each discovered manifest again with that exact package;
  3. record the source revision, engine version, manifest version, and artifact hash;
  4. rebuild Lambda ZIPs and container images without vendored Linking code;
  5. run scan, report, ZIP, image, startup, and end-to-end request tests;
  6. promote only immutable outputs produced by the verified build.

Rollback must also recompile

If APIZIT rolls back to 0.4.0, it must restore the exact 0.4.0 dependency and deploy an artifact freshly compiled by 0.4.0, or a preserved immutable 0.4.0 output with proven provenance. A new artifact cannot be made compatible by editing its engine field.

Wait for the canonical signal

Follow the 0.5.0 / RC draft for publication gates. PyPI will be the canonical source of package files; these Pages notes will become the canonical explanation only after they name an observed published version.
